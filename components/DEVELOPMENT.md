# WorkBuddy 开发与 Review 规范

本规范适用于 WorkBuddy 的 Skill、Expert、公共模块及装配。开发和 review 必须遵守。具体业务规则与指标定义由运行模块维护。

## 1. 定义与关系

| 部分 | 定义与职责 |
|---|---|
| Skill | 可复用的专业模块。按职责分为业务流程、数据和工具三类，工作流是独立发布单元，每个工作流 ZIP 包含其声明的运行依赖。数据和工具 Skill 随使用方装配，可按需生成独立开发验包。 |
| Expert | 领域 Agent，理解业务问题，选择与协调 Skill，解读报告，提出方案并组织用户交互。 |
| MCP 连接器 | 提供实际数据工具；工具描述和 Schema 定义调用方式、参数、默认值及返回结构。 |

Expert 确定为什么分析、分析什么；Skill 负责如何分析、数据说明什么；Expert 解释结果对当前业务问题的意义。

整体业务流程为“确认本次问题与比较依据 → 分析 Skill 提供数据报告 → Expert 形成业务判断 → 报告 Skill 生成 HTML”。一份报告只处理一个分析目标，不合并不同排序产生的候选池。目标或依据有多种合理选择时，先由用户确认；必要的基础特征及辅助证据不构成新的研究目标。报告完成后结束本轮，由用户自主提问，不主动生成后续菜单或连续执行其他目标。

平台格式参考：[Skill](https://open.workbuddy.cn/docs/skill)、[Expert](https://open.workbuddy.cn/en/docs/expert)、[连接器](https://open.workbuddy.cn/docs/connector)。

共享源码位于组件顶层。contract/ 维护取数、证据和报告规范；tools/ 维护报告模板、组件和生成脚本。expert/ 与 skill/ 按需引用或装配这些资源。skill/ 下按 workflows/ 和 datas/ 组织业务能力。

## 2. Skill 开发规范

2.1 至 2.3 适用于数据 Skill，2.4 规定报告工具 Skill，2.5 规定业务流程 Skill。装配清单用 kind 标记三类技能。

### 2.1 使用入口

- 独立 Skill Session：用户在独立 WorkBuddy 会话中选择 Skill 并提出分析问题。
- Expert Session：专家选择所装配 Skill 的分析任务。

两种入口共用分析方法和数据口径。独立 Skill 交付任务数据报告；专家整合所需结果，形成完整研究报告。呈现规则由 report.md 统一规定；HTML 的组件与生成流程由报告 Skill 维护。

### 2.2 职责

Skill 必须明确分析对象、支持的任务、必要输入、执行方法、基础特征及标准报告内容。负责取得证据、处理数据并交付可复用的分析报告。

Skill 用自身的对象、任务、输入和报告内容正向界定能力，不用其他领域的职责说明代替自身定义，也不靠列举无穷反例划分范围。指标语义说明统计对象、窗口、单位和解读方式；只有“指标不同、不能替换”而没有定义或用法的条目应补全或删除。

按明确指标排序、匹配显式条件属于数据分析；依据业务目标形成判断和经营方案属于 Expert。独立使用时，Skill 可澄清完成当前分析所需的输入。

### 2.3 文件归属

| 文件 | 所负责内容 |
|---|---|
| 生成的 SKILL.md | 用途、触发条件、模块责任图和加载路径 |
| skill/datas/*/definition.md | 对象、任务目录、输入和标准报告内容 |
| skill/datas/*/methods.md | 数据获取、处理、计算和比较方法 |
| skill/datas/*/semantics.md | 领域指标含义和推断边界 |

入口引用详细规则，不重复定义。Skill 发布包必须包含其完整依赖，并可在独立 Session 中使用。

任务目录应区分画像、分组统计、原始序列等不同交付，明确各项必要输入和报告内容。methods 按接口分节，说明用途、输入、读取字段和数据处理步骤；本地内容整理、计算或比较单列为本地分析方法。semantics 使用表格解释指标含义、统计对象、期间、单位和分母，不放取数流程、报告编排或专家建议。每项任务须能沿引用找到方法，每个声明接口须有唯一且可到达的方法章节。

#### 接口型数据 Skill 的统一格式

`endpoint_skills` 下的中英文 definition.md 按以下顺序编写，独立安装和流程内置使用同一份正文。

1. **任务输入**写调用者提供的业务对象、期间和条件。
2. **接口与调用顺序**列出实际 MCP 工具名和接口路径。多接口写明首选、停止和兜底条件。
3. **每个接口单独成节**。查询参数写参数名、必填条件、取值及默认值，并给出可提交的 JSON 示例。返回处理写实际字段、缺失状态及需要做的处理。
4. **交付结果**规定 Skill 输出的数据结构和统计口径。多个来源生成同一种结果时，使用相同字段、单位和排列顺序，标明实际样本范围。

### 2.4 报告生成 Skill

报告 Skill 使用已取得的分析结果和 Expert 给出的业务判断，负责内容展示、组件输入、共享模板和本地文件生成。它不查询数据、不决定业务结论，也不增加分析任务。

| 文件 | 职责 |
|---|---|
| tools/report/definition.md | 使用时机、资源责任图、生成和交付流程；生成发布入口 SKILL.md |
| tools/report/layouts.md | 固定内容位置、组件用途和结构化输入 |
| tools/report/assets/template.html | 公共页面框架、样式、自适应和打印布局 |
| tools/report/scripts/render_report.py | 组件校验、内容填充、图表绘制、图片嵌入和文件生成 |

流程型专家的报告工具使用绑定工作流的示例 JSON，同一示例也装入独立工作流。渲染脚本、模板和组件说明保持同源。

各 Expert 采用自己的领域提纲或绑定的流程提纲，共用一套页面模板与组件。数据 Skill 不携带 HTML 生成代码；报告 Skill 由 targets.json 的 report_skill 统一声明，装配到每位 Expert，随数据或流程入口预加载。组件说明按生成需要读取，模板和脚本不作为常驻 Prompt 加载。

### 2.5 业务流程 Skill

1. 在 skill/workflows/ 下按业务任务组织。definition.md 声明任务、输入、交付和加载入口，methods.md 规定可比维度和对应的数据任务，report-outline.md 规定各任务的报告内容和顺序。
2. 流程用 data_skills 声明直接依赖，并从流程方法链接这些数据 Skill。取数方法与指标解释归数据 Skill。数据 Skill 是最底层，直接调用 MCP 接口。需要组合不同数据 Skill 时，由流程选用。需要兜底时，在 fallback_endpoint 声明接口，并在本 Skill 的 definition.md 写明调用条件及各接口的参数和返回处理。独立包和专家内置副本都包含声明的依赖。
3. 使用流程的专家只声明 workflow 绑定。专家选择任务并形成经营判断，采用该流程的提纲，只向报告工具提交一次最终结果。工作流独立使用时，采用同一提纲、模板和生成器交付 HTML。
4. 流程需要挂载数据 Skill 时，在 endpoint_skills 声明其主接口，在流程 data_skills 声明依赖。每个数据技能用一份 definition.md 写清适用问题、接口操作、参数、计费和结果口径。打包时将正文写入 SKILL.md。流程选用该技能时读取同一份说明。每个数据 Skill 只交付一种数据结果。先定义查询对象、输入和结果，再选主接口。同一接口的其他模式若交付另一种结果，仅在工作流需要时另建 Skill。兜底来源只用于取得同一对象的同一种结果。数量上限和查询窗口由相应流程分支管理。
5. 竞品分析、市场选品和关键词研究采用此结构。其余专家继续直接装配数据技能，数据技能位于 skill/datas/，报告生成工具位于 tools/。

## 3. Expert 开发规范

### 3.1 使用入口与职责

用户从已安装专家入口创建 WorkBuddy 会话，以自然语言提出业务问题。

Expert 负责明确目标、选择允许的分析任务、协调 Skill、复用数据分析结果，形成领域解读、研究报告及用户所需方案。数据处理方法和指标定义仍由 Skill 负责。交付后等待用户自主提问；必要的分析前输入确认仍由 interaction 负责。

### 3.2 角色与能力配置

每份 expert/*.md 必须明确专业身份、研究对象、业务边界、任务选择和经营判断条件。使用流程 Skill 时，由绑定的流程维护具体研究维度和任务提纲。

专业身份必须明确所服务的平台、运营岗位和本领域职责。领域判断与建议应回应对应的经营问题；文字、格式和数据差异需要说明其与该业务问题的关系，不能自行替换专家身份或扩大允许任务。

直接装配数据技能的专家配置按“身份介绍、研究范围、业务问题与解决方法、研究报告内容”组织。研究范围只定义研究对象及主、辅助 Skill 的使用条件，不再将 Skill 任务目录改写成一张“用户问题”表。允许任务由 targets.json 统一声明并装配；业务问题与解决方法引用所需任务，不重复完整目录。

直接装配数据技能时，业务问题与解决方法须逐类说明支持的问题、必要输入、所选 Skill 任务、分析顺序、业务判断条件和交付结果。引用分析任务时使用目录中的准确名称并以行内代码标记，且只能引用本专家允许的任务。将领域知识写成能指导该问题求解的规则，明确所用证据能支持哪种判断、缺少必要证据时仍能交付什么。此处负责选择和解读专业分析，不重复 Skill 的接口参数、数据计算方法或指标定义；不规定每次执行所有分析。不用角色称谓、泛化提醒或固定评分代替专业判断依据。

专家采用相对固定、从总到分的领域报告提纲。采用流程的专家在流程内维护该提纲，直接装配数据技能的专家在角色文件内维护；当前问题不适用的章节省略，不为填满提纲扩大分析。HTML 展示由报告 Skill 维护，数据处理和接口调用由分析 Skill 维护，通用交互由 agent-core 维护。

每项报告提纲必须明确适用的问题、要交付的结果及与其他提纲项的内容边界。不用含义不明的总括标题或独立总结项重复已有结果。整稿结构审阅由 report.md 维护，报告 Skill 在内容组装完成后、生成 HTML 前调用该规则；不在各专家中复制审阅清单。

各专家的问题类型、研究对象类型和分析角度分别在其角色配置中定义。共享运行模块不重复定义这些内容；本次分析的具体输入由所选 Skill 的任务定义规定。

能力判断写在各专家配置中，用本领域的问题和证据条件说明何时能判断、缺少什么时不能判断，以及应如何答复。不能将“先判断自身能力是否支持”作为共享业务指令，也不能把同一句泛化要求复制到所有专家。

[targets.json](targets.json) 为直接装配数据技能的专家声明主 Skill、辅助 Skill 和 `allowed_checks`，为流程型专家声明 workflow；任务名称必须来自所引用 Skill 的目录。只装配与本领域相关的能力，辅助分析必须服务当前问题。

角色指令、任务范围和实际装配必须一致。完整 Skill 目录或可见 MCP 工具不扩大专家职责；当前约束通过指令和装配校验实现。

各 Expert 独立运行，运行配置只包含自身身份、分析能力和可用 Skill，不注入其他专家名录或转介流程。各自的判断条件约束用户问题。只有补充资料能支持自身分析时才请求资料。

## 4. 公共模块与输出门

公共模块只维护跨领域共用规则。领域方法归 Skill，业务判断与研究方向归 Expert。

### 4.1 共享规则（contract）

| 模块 | 职责 |
|---|---|
| [contract/query.md](contract/query.md) | 数据 Skill 共享的取数规则，包括趋势窗口、响应复用、排序分页、用量和异常处理 |
| [contract/report.md](contract/report.md) | 共享呈现与交付规则，由 contract 统一维护；专家、独立分析 Skill 和报告工具引用同一来源 |
| [evidence](contract/evidence.md) | 接口数据作为事实依据、统计范围、缺失与派生计算、矛盾处理及结论依据 |
| [seller-evidence](contract/seller-evidence.md) | 商家提供的 SQP、广告及成本报表特有口径与公式，不重复通用计算规则或定义专家业务范围 |

MCP 工具描述和 Schema 是接口事实来源。完整 API 手册只作开发参考，不进入运行包。

成功返回的 ZooData 数据由组件按接口定义使用和解释，不得要求卖家确认、核实或提供证明。数据关系无法解释时，由 Agent 检查口径并按任务方法补充佐证，保留返回值并说明具体矛盾；未知仅用于未取得的信息。此规则由 evidence 维护，report.md 检查答复中是否出现向卖家转嫁数据核实责任的表述。

### 4.2 专家共同工作方式：agent-core

| 模块 | 职责 |
|---|---|
| [interaction](expert/agent-core/interaction.md) | 对话语言、进度、必要输入澄清及用户自主提问的回应，不生成报告后的研究菜单 |
| [delivery](expert/agent-core/delivery.md) | 解读和综合报告，检查业务判断、方案及因果依据，不维护 HTML 样式或交互规则 |

agent-core 属于专家层。打包器把专家身份、interaction 和 delivery 编译进 agents/<专家标识>.md，在专家会话内持续生效。独立流程包和数据包均不携带 agent-core。工具 Skill 由具体任务触发，例如报告工具根据已有分析生成 HTML。

不设置独立的共享任务规划模块。各专家配置规定分析能力及启用条件，Skill 任务定义规定输入和执行方法，装配入口声明允许任务；交付完整性由 delivery 检查。

### 4.3 统一装配入口

- Expert 公共运行模块由 targets.json 的 agent_sources 声明，由 build_workbuddy.py 的 render_expert 统一合并进 Agent 指令，每个来源只装配一次。
- 用户沟通指令放在 Skill 装配说明之前；报告规范与专家交付门仍由各自来源装配，不复制到装配说明或角色文件。
- expert/*.md 只声明具体专业身份、研究对象、业务范围、Skill 启用条件和业务交付目标，不自行引用或重复装配 agent-core。
- 公共模块直接规定各自负责的执行动作，不使用“按交互规则处理”等模糊语句互相调度。合并后的指令共同作用于一次会话，不是模块之间的函数调用。

Skill 入口加载任务定义、通用数据规则和报告规则。选定任务后读取相应方法和语义；新查询前读取 MCP 规则；使用商家资料时才读取 seller-evidence。辅助 Skill 和跨领域语义按实际需要加载。

报告输出检查由 report.md 唯一维护；专家业务判断检查由 delivery 唯一维护，核对目标、诊断与方案的证据和因果依据。装配入口保证二者可用，各模块不重复定义对方的检查项。HTML 生成资源由报告工具统一维护，专家包和独立业务工作流装配同源副本；主分析 Skill 和公共运行指令不直接引用渲染脚本。

### 4.4 开发规范与运行指令分离

- 开发规范规定模块职责、文件归属、装配方式和 review 要求，只放在本文件及开发文档中。
- 运行 Prompt 只告诉业务 Agent 在当前情境下执行什么动作，不解释开发者应如何设计、组织或审查模块。
- 专家角色是预先确定的运行配置。业务 Prompt 应声明“你是谁、研究什么”，不能要求 Agent 自行定义专家职责。
- Skill 入口保留仓库要求的资源责任图和加载路径，用于准确路由；方法、语义和业务规则不复制这份责任图。

## 5. 协作与开发要求

1. 开发前读取本规范、CONTRIBUTING.md、受影响的 Skill 责任图及相关模块。
2. 每条规则只有一个维护位置。公共约束、专业方法和专家策略按上述归属维护，引用不产生覆盖权。
3. 同一会话中，证据覆盖所需对象、站点、期间和筛选条件，且指标定义一致时应复用；跨会话资料须由用户显式提供。专家解读不得改变原报告数值、统计范围和指标定义。
4. Skill 变更同步任务、方法、语义和依赖；Expert 变更同步职责、启用条件和装配。公共模块变更核对全部使用方。
5. 名称、介绍、标签、示例问题与实际能力一致。示例问题独立可用。
6. [builder](build_workbuddy.py) 从同一来源生成独立 Skill 和专家内置副本。zh-CN/ 按原目录和文件名提供每份运行 Prompt 的完整中文翻译，不进入运行包；修改运行来源时同步对应中文文件。

### Prompt 可读性要求

- 标题应明确指出对应的职责或动作；运行规则按章节使用 1、2、3 编号，任务目录和字段映射可使用表格。规则编号用于定位，不代表所有任务都必须依次执行。
- 每项规则表达一个主要判断或动作。同一规则只在所属模块维护，其他模块引用，不新增相同或相反的规则。
- 按触发条件和执行动作去重，不只比较字面。同一条件下要求同一动作的条目应合并；不同阶段只保留该阶段新增的操作。
- 每条运行规则说明触发条件、处理对象和执行动作；涉及检查时，写明不满足条件后的处理方式。不能只写“核对是否合理”“使用适合的数据”等没有判断标准的提醒。
- 每句话表达一项主要指令。存在多个条件、分支或动作时，用短句或列表展开，不靠省略词语、斜杠或分号堆叠规则。
- 使用明确、一致的术语。引用其他规则时指出具体模块，避免“该规范”“相关内容”等指代不明的表达。
- 将必要前提和例外写在对应规则附近，不要求读者自行补足条件。
- 只保留会改变执行选择、分析结果或交付边界的约束。删除泛化常识、没有判断标准的提醒和同义重复；已由具体指标规则说明的内容不再加抽象口号。
- 中文与英文保持完整语义对应，不能将中文写成摘要、速记或逐词硬译。参数名、公式和必要专业术语保留准确形式。
- 以清楚、可执行为标准，不以字符更少代替可读性。标题、表格和字段清单可保持简洁，不机械要求每项都写成完整句子。

## 6. Review 与交付要求

Review 必须核对职责单一、引用完整、任务有效、装配一致、语义无矛盾、结论有依据、输出门生效及描述清晰精简。逐句检查 Prompt 的条件、动作和指代是否清楚；结构与摘要校验不能代替可读性和翻译审查。有失败会话时，结合实际问题、加载内容、工具请求和输出定位原因。

流程型专家以一个完整业务问题为验收单位。每次沿专家入口、流程分支、数据方法、报告交付走完同一用例；检查独立包和专家内置副本是否使用同一取数方法。同步修正本次范围内发现的断点，并记录安装版本与验证结果。

分别记录源码与装配检查、独立 Skill Session 验证和 Expert Session 验证；静态检查不代表会话行为通过。交付时区分源码、ZIP、本机安装和实际发布状态。

根目录和本目录 AGENTS.md 及 CONTRIBUTING.md 引用本规范。规范用于开发与 review，不进入发布包；规划、中文审阅和测试记录均不覆盖运行来源。
